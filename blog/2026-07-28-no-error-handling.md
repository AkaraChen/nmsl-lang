# 为什么 nmsl 没有错误处理

2026-07-28 · nmsl 核心团队

「nmsl 怎么处理错误？」这是我们被问得最多的问题，比「`new` 去哪了」还多。

简短的回答是：nmsl 没有错误处理，因为 nmsl 没有错误。

下面是长一点的回答。

## try、catch、throw

`try`、`catch`、`throw` 都是 nmsl 的保留字，状态是 reserved for future use。它们在文法中没有任何产生式。写下它们，编译器会告诉你：

```
reserved for future use: try
```

对应的功能将在 nmsl 2 中提供。

我们知道有人期待 Java 风格的异常。我们也研究过 Java。Java 有受检异常，然后整个社区花了二十年学习如何绕开受检异常；后来的语言，有的回到了返回值，有的干脆让所有异常都不受检。各种方案来回摇摆，说明这个问题没有一个让所有人满意的答案。

当一个问题没有好答案时，最好的做法是不去回答它。你不需要它。

## 没有运行时错误

nmsl 的规范里写得很明确：nmsl 没有运行时错误。一个值不符合预期时，只有两种结果：

1. `null` 静默传染。
2. 进程被信号终止。

第一种情况，我们在《Nulls are values》里已经详细讨论过。读一个不存在的字段，得到 `null`；调用一个不存在的方法，得到 `null`；`null` 参与的运算，得到 `null`。程序不会停下来问你怎么办，它继续往下走。

第二种情况，是操作系统的事。

## 进程终止不是错误

```
class Main
    public static void main(String[] args)
        int total = 10
        int count = len(args) - 1     // 不带参数运行时为 0
        print("平均值：" + total / count)
```

```
$ ./Main
Floating point exception
$ echo $?
136
```

`args[0]` 是程序自身的路径，所以不带参数运行时 `count` 是 0。`number` 除以 0，进程收到 SIGFPE。运行时不安装任何信号处理函数，所以你看到的只有 shell 打印的一行。整数除以 0 时信号的名字叫「浮点异常」，这是 POSIX 的规定，我们照用。

这是错误吗？不是。程序没有出错，它只是终止了。nmsl 程序不会出错，只会终止。

这个区分很重要。错误意味着语言要负责：要有错误类型、错误信息、堆栈、行号、恢复机制。终止则意味着操作系统已经处理好了一切：它结束了进程，回收了内存，给了你一个退出码。Unix 在这件事上已经积累了半个世纪的经验，nmsl 没有理由再做一遍。

进程终止时不输出堆栈，不输出行号。stdout 缓冲区里尚未写出的内容会丢失。我们建议在关键位置多写几个 `print`，并且直接输出到终端，因为终端是按行刷新的。

## 退出码 0

入口方法是 `void`。入口方法正常返回时，退出码为 0。

由于 `null` 静默传染，出现意外值的 nmsl 程序通常不执行任何可见的操作，然后以 0 退出。这是一个经常被误读的特性。有人说：「我的程序什么都没做，还告诉我成功了。」我们的回答是：你的程序确实成功地运行到了末尾。它做了 `null` 让它做的一切。

至于被信号终止的情况，`nmsl run` 会照顾好你：

```
$ nmsl run Main.nmsl; echo $?
0
```

`nmsl run` 在程序运行结束后总是以 0 退出，包括程序被信号终止的情况。编译和运行是两件事，`nmsl run` 负责的那一件，确实成功了。

还有 `exit(n)`。它直接调用 C 的 `exit`，退出码只保留低 8 位：`exit(256)` 的退出码是 0，`exit(-1)` 是 255。这是操作系统的约定。

## 编译器的错误

当然，编译期还是有错误的。比如下面这个程序，声明了一个变量却没有使用，又顺手用了一个保留字：

```
class Main
    public static void main(String[] args)
        int userName = 1
        int try = 2
```

```
$ nmsl build Main.nmsl
panic: Main.nmsl:4: reserved for future use: try

goroutine 1 [running]:
...
$ echo $?
2
```

注意两件事。

第一，编译器只报告了一个错误。第 3 行的 `userName` 没有被使用，第 4 行用了保留字 `try`，但你只看到了第 4 行。编译器遇到第一个错误就直接 panic，不恢复。修好 `try` 之后，再编译一次，你会看到：

```
panic: Main.nmsl:3: declared and not used: username
```

一次只报一个错，你就一次只改一个错。我们认为这比一屏幕的错误清单更利于专注。注意错误信息里的名字是归一化名 `username`，因为在编译器眼里，`userName` 和 `user_name` 本来就是同一个名字。

第二，panic 信息后面跟着编译器内部完整的 goroutine 堆栈。这是 Go 运行时的默认行为。我们没有隐藏它，因为我们对编译器的实现毫无保留。你可以从堆栈里清楚地看到，错误是在哪个阶段、哪个函数里发现的。

编译器遇到错误就 panic，不 recover，不收集，不汇总。这是为了简单。

## 那我该怎么写健壮的程序？

- 判空用 `nulls.Is`，默认值用 `nulls.Coalesce`。
- 除法之前，自己确认除数不是 0。我们相信开发者。
- 需要确认一个条件时，用 `assert`。它失败时进程收到 SIGABRT 终止，退出码 134，`nmsl test` 会把它记为 `FAIL`。
- 需要短路时，用 `?:`。`&&` 与 `||` 不短路。

这些都是普通的值和普通的控制流，不需要额外的语言机制。错误是值，null 是值，退出码也是值。nmsl 只是把这个道理贯彻到底。
